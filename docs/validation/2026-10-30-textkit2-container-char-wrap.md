# TextKit 2 container-level character wrapping control

Issue #75 remains unresolved. This generated-data control applies
`NSTextContainer.lineBreakMode = .byCharWrapping` directly to a native TextKit 2
`NSTextView`. Earlier character-wrap evidence used TextKit 1 and paragraph-style
settings, so this isolates the current editor's container-level setting. No
application source or user file is involved.

## Result

The optimized probe assigns the same generated Arabic/emoji paragraph form,
then requests the first viewport with TextKit 2. Both 1 MiB and 10 MiB runs
reached `stage=assigned` and failed to return from viewport layout within the
unchanged 10-second diagnostic bound. The harness terminated each generated
process at that bound. No line coverage or geometry was returned, so direct
container-level character wrapping does not establish a correction.

## Reproduction

```sh
xcrun swiftc -O -parse-as-library -target arm64-apple-macosx14.0 -swift-version 6 \
  -warnings-as-errors -module-cache-path /private/tmp/notehush-modulecache \
  docs/validation/reproducers/TextKit2ContainerCharWrapProbe.swift \
  -framework AppKit -framework CryptoKit -o /private/tmp/TextKit2ContainerCharWrapProbe
```

Run the binary separately with `1048576` and `10485760`, each with a 10-second
process bound. The probe emits only the generated byte count before entering
layout; the bounded host retained both timeout outputs under the ignored local
`build/logs/TextKit2ContainerCharWrap-20261030/` directory.
