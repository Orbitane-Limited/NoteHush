Native/unbounded, explicit RTL, disabled optional ligatures and forced RTL embedding variants all time out for both sizes. Apple's bounded option returns no typesetter (191/236 ms), which is not a successful rendering result. The exact previously compiled Swift source is also retained as a [standalone reproducer](reproducers/README.md). ## Asynchronous layout hypothesis

A separate generated, sandboxed AppKit window tests the public queue APIs with 256 KiB and exact text preservation. Assigning the layout manager queue still blocks at initial layout for the ten-second process bound. Assigning each layout fragment's queue lets initial layout return, permits five main-actor ticks over one second, and permits normal application termination. Eight layout operations remain pending: this does not prove completed rendering, editing/caret correctness, cancellation or acceptable CPU/memory.

Apple documents the [fragment layout queue](https://developer.apple.com/documentation/appkit/nstextlayoutfragment/layoutqueue) as asynchronous. A small real-app prototype exists only on private `validation/issue75-async-layout` at `0b8d3b4`, built with the exact optimized target and product sandbox. It is not a shipping policy. Its first driver had a retained artifact-root error after compilation; the corrected preparation then stopped at the disk headroom check before launching a workload. No assertion, file size, target or timeout was relaxed.

Ten unused NoteHush compiler caches were subsequently reclaimed after checking their scope and open files; no product, fixture or result was removed. Later disk availability fell below the unchanged ten-percent headroom policy while unrelated Swift builds were active. Only process names and working-directory classification were used to distinguish that activity; unrelated files, arguments and applications were not inspected or interrupted. These later conditions do not establish continuous system monitoring during earlier measurements. Native runs remain paused until capacity and contention checks permit them.

The queue prototype also requires a stronger completion oracle: `NSTextLayoutFragment.state` must reach `layoutAvailable` before its line fragments establish completed layout. Main-actor ticks, queued operations and a durable checkpoint alone cannot establish visible glyphs. An operation cancellation request does not prove that an already-running Core Text call has stopped. The prototype must remain experimental until those semantics and resource bounds are demonstrated.

After disk availability recovered and two thirty-second readiness samples found no competing native work, the private real-app prototype completed the unchanged two-case long-paragraph diagnostic at 03:03 UTC. Both ASCII and mixed 10 MiB cases passed every exact source/recovery/file identity/selection/viewport/tab/window and normal-Quit oracle. Individual request-to-checkpoint observations were 233.130 and 299.804 ms. App source remained clean `0b8d3b4`; binary `96491f1cd13a05af5dce5dcaf7a2e1a2fa9aa2a533377d32cb06363804f36129` and exact product sandbox were verified before and after. This is functional progress, not a complete rendering or performance acceptance result. It uses the same original two-case host and limits as the earlier retained failures; it does not retry those binaries or replace their outcomes.

A separate sandboxed completion diagnostic tracks weak fragment references and reads line ranges only after the public `layoutAvailable` state. Its first 256 KiB ASCII case was interrupted at tick 27 of 40 when the scheduling pause raced with its start. This remains an incomplete case without a normal-termination pass. Its source, product, partial output and explicit interruption correction are retained. No process from that invocation remained active before the three previously unlaunched cases continued with the same binary and ten-second process bound; the original four-case matrix is not complete or passing.

Those remaining cases all preserved exact text and terminated normally after forty 200 ms main-actor ticks. The 10 MiB ASCII fragment reached `layoutAvailable` with zero pending operations and contiguous coverage of all 10,485,760 UTF-16 units across 105,917 native line fragments. Both 256 KiB and 10 MiB mixed paragraphs remained at estimated usage bounds with eight pending operations. Full line coverage was therefore not established for either mixed case. This rejects asynchronous queuing alone as a completed solution; it does not turn an unfinished layout into a passing editor or certify physical rendering, cancellation after tab close, or acceptable sustained resource use.

The next step is to identify a layout correction that establishes complete glyph coverage, then test native geometry, editing, recovery, viewport and lifecycle semantics. Pending background work must not be relabeled as a fully usable editor. Any final change needs focused tests, complete original performance regressions, full native CI/review and the normal issue PR workflow. File limits, paragraph breaks and text bytes remain unchanged; no release, upload or App Store readiness claim follows from these diagnostics.
