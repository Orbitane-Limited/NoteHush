# Native interaction measurement protocol

Issue [#43](https://github.com/Orbitane-Limited/NoteHush/issues/43), engineering version 0.1.0 (1). The implementation builds and its repository/core/archive checks pass. **Native interaction correctness, complete observations and final-head CI remain unverified.** The first attempt failed during XCTest automation initialization before any scenario executed. No latency result or product-budget acceptance is derived from that attempt.

## Timing boundaries

The optimized UUID-isolated app uses `PerformanceApplication`, an `NSApplication` subclass compiled only under `NOTEHUSH_PERFORMANCE_TESTING`. Apple's [sendEvent documentation](https://developer.apple.com/documentation/appkit/nsapplication/sendevent(_:)) describes this main-event-loop dispatch boundary and supports overriding it. The override first requires an active app, its visible key window, no attached sheet, and the editable `note-editor` as first responder. It recognizes only the generated unmodified `x` action and Control-Tab/Control-Shift-Tab actions. No character value, text, path, bookmark or clipboard content is emitted.

`TypingEventDispatch` and `TabEventDispatch` use `OSSignposter` around `super.sendEvent`. The interval begins after the eligibility checks and ends immediately when native dispatch returns. It includes synchronous event routing, editor/command work and callbacks inside that call. It excludes event creation, automation delivery and prior queuing, and does not await later status/recovery tasks, deferred drawing, compositor presentation or display scan-out. It never forces extra layout or drawing. A monotonically increasing fixture-window identifier is published after the endpoint; each measured action must advance it exactly once. Missing or duplicate eligible dispatches fail the native scenario.

The separate `XCTClockMetric` spans the test driver's `app.typeKey` call, with manual start immediately before and manual stop immediately after. It includes XCTest input synthesis, delivery and synchronization overhead. It is an **automation round trip**, not product input latency. The OS signpost and XCTest monotonic durations are exported in seconds; no timestamps from different clocks are subtracted, and the overlapping intervals must not be added. Apple's [XCTOSSignpostMetric documentation](https://developer.apple.com/documentation/xctest/xctossignpostmetric) defines matching begin/end collection. The installed `XCTMeasureOptions.h` confirms manual collection boundaries and the extra excluded framework warm-up iteration.

Neither interval establishes the PRD's event-to-visible typing target or a fully presented tab transition. Apple's [draw documentation](https://developer.apple.com/documentation/appkit/nsview/draw(_:)) also permits drawing nonvisible cached regions; such a callback alone would not prove display presentation. These dispatch observations are explicitly diagnostic. The 16.7 ms typing and 50 ms switching product targets remain unchanged and unverified until the relevant boundary and reference hardware are measured.

## Fixtures and functional oracles

There are four scenarios, each requesting 20 measured iterations plus XCTest's one framework warm-up. Typing uses two generated 1 MiB drafts, selecting either ASCII or Arabic/combining-mark/emoji CRLF text. The other draft retains a distinct `y` edit while every selected-tab `x` edit is undone and checked. Switching uses 20 open 256 KiB drafts, selecting the ASCII or mixed-script adjacent destination; both viewports are visited before measurement. The two tabs retain distinct edits through each switch/return, then each tab's own Undo restores its original bytes. Two closed 256 KiB drafts are retained in each scenario.

Each open tab has a deterministic middle text anchor, three-point offset and a UTF-16 caret ten logical lines below that anchor. Before each measured action, the driver checks the identified app is active and verifies selected tab and source digest. Native dispatch also checks actual keyboard focus at its entry. After collection stops, checks require exactly one dispatch, the intended selected tab and exact expected text digest. Text replacement expectations use UTF-16 `NSRange`, not grapheme counts. These are spaced single-key measurements, not continuous typing or real IME-composition certification.

After a scenario's measurements, the driver visits every open buffer, verifies exact digests and returns to the original selected tab. It quits with Cmd+Q, verifies the owned process terminated, relaunches and repeats every-buffer verification before another normal Quit. Host verification checks all open/closed text digests and identities, order, selected tab, advanced revision, exact saved selections, logical visible lines, offsets within one point and horizontal position. The line oracle counts LF UTF-16 units in the generated CRLF fixture; a mixed-direction line's leftmost glyph need not be its first logical character.

`PerformanceFixtureHarness` retains ownership only after verifying returned bundle URL and identifier. Missing/invalid UUID guards run before fixture setup. Manifests select the complete launch or interaction scenario group; setup never replaces existing evidence. Cleanup requires no running performance app and removes only the generated UUID workspaces. The sandboxed UI runner reads its generated manifest and never writes another app's recovery container.

## Running and extraction

Run `bash scripts/test_interactions.sh` after CI and all other local GUI automation finish, on an awake/unlocked desktop with exclusive keyboard/mouse use. The script builds the optimized app, verifies its exact four sandbox entitlements, prepares fixtures and records source/binary/hardware/toolchain/power/thermal/display/cache conditions. Each scenario uses one fresh process followed by warmed repeated interactions and an untimed final restart. This differs from the launch protocol's fresh process per iteration.

The script selects only `InteractionPerformanceTests`. The original launch script explicitly selects only `LaunchPerformanceTests`, preserving its three fixtures and original intervals. `summarize_performance.py --suite interaction` requires all four cases, exactly one test run per case, each case's correct dispatch identity plus the clock metric, explicit seconds units and at least 20 finite nonnegative observations each. It rejects missing/duplicate cases, retries, extra/wrong intervals, wrong units, nonfinite/negative/Boolean samples and incomplete results. Slow values are retained. A passing four-case collection would contain 160 observations; the first attempt produced none.

The manually dispatched `Application performance` workflow selects `launch` or `interaction` through a fixed choice and shell case, on the same single self-hosted runner as functional CI. Normal CI only builds the optimized target; it does not run measurements. Original functional timeouts and assertions remain unchanged. Performance cases retain the existing 600-second allowance for their repeated actions and recovery checks.

Shipping Release uses the ordinary `NSApplication` and excludes the subclass, event markers, UUID override and readiness probes. Archive validation checks both metadata and executable bytes. No entitlement or required-reason API declaration changes are introduced.
