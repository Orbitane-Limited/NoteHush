# Native large-file opening protocol

Issue #73 adds an opt-in diagnostic for the open-file and durable-recovery path. It does not change shipping code, supported file limits, functional CI timeouts or the existing launch, interaction and idle protocols. Its measurements contribute to #12; they do not alone satisfy the PRD's one-second, interactive-window target.

The [first complete baseline](validation/2026-09-09-large-file-opening-baseline.md) passes all 40 correctness observations. ASCII/mixed-script request-to-checkpoint p95 is 414.136/9,654.208 ms on the recorded M4 Pro. Every sample remains retained; mixed-script and interactive-window performance still require work and final validation.

## Workload and timing boundary

`NOTEHUSH_EXCLUSIVE_INPUT=1 python3 scripts/test_large_open.py` builds the existing `ReleasePerformance` app and the optimized, host-only `LargeFileOpenHarness`. Arrange exclusive, awake GUI use and finish CI, compiler and profiling jobs first. The wrapper requires a clean committed source tree, exact optimized app identity and product sandbox permissions. It checks the existing disk policy plus 1 GiB build headroom before building, then plus 512 MiB for retained fixtures before launching. This is an operator protocol; the environment flag is an attestation, not automatic proof of exclusivity.

Two generated UTF-8 files contain exactly 10,485,760 bytes each: ASCII and Arabic/combining-mark/emoji, both CRLF. Each begins with one 16-byte ASCII header and has 655,359 complete 16-byte repeated lines. The ASCII fixture has 10,485,760 UTF-16 units; the mixed fixture has 7,208,965. The generator never truncates a Unicode scalar or CRLF. Independent small byte oracles and complete fixture counts are tested.

Each file has 20 observations, in fixed ASCII-then-mixed order, using 40 fresh app processes and UUID workspaces. Filesystem caches are warm after preparation; this is not a cold-storage experiment. No input events, accessibility commands, private API or shipping test hooks are added. Public LaunchServices requests identify the exact dedicated app bundle and returned PID. The harness rejects an already-running performance app and proves missing/invalid workspace values exit with `EX_CONFIG` before collection.

After a fresh process has published a complete empty checkpoint and become active, the timer starts immediately before the host requests opening the file. It stops when the independent reader observes a stable checkpoint with both tabs, the opened tab selected, its file binding and every expected UTF-8 byte. This includes LaunchServices, app processing, recovery scheduling and I/O, host polling, checksum work and JSON decoding. Record the LaunchServices return interval separately. **Neither interval measures a physical frame or proves that the window remained interactive.** Do not combine these samples with native event-dispatch, XCTest round-trip or first-frame intervals.

Initial checkpoint and activation observations each have a ten-second bound. The open observation has ten seconds starting at the request, including LaunchServices return; normal Quit has twenty seconds. A slower observed checkpoint is retained as a failed observation, not filtered or retried. Stop at the first failure. No CI speed assertion or budget exception is introduced.

## Correctness and retained evidence

Outside timing, every observation verifies all tabs and IDs/order, exact UTF-8, selected tab, UTF-16 selection, logical viewport, preferences, window geometry, file encoding, source identity, digests and a nonempty sandbox bookmark. Quit must terminate normally. An independent complete checkpoint read after termination must preserve those assertions, and the external source file must still contain its original exact bytes. The reader is shared with `ColdLaunchHarness`; its independent schema-6/checksum and stable-generation algorithm is unchanged.

The wrapper creates a private, unique `build/logs/LargeOpen-<UUID>` directory. The journal appends and synchronizes attempt, identified process, timing and post-Quit verification records. It records timing before later assertions so failure does not erase an observed duration. A final completion record alone is insufficient: the summarizer also requires successful collector exit, unchanged clean source, unchanged app/harness hashes, valid signatures before/after, every expected record and every oracle. It rejects duplicates, retries, reordering, unknown fields, false checks, wrong units/types, missing cases and nonfinite values. Median is the arithmetic middle pair; p95 is nearest rank (sample 19 of 20). All observations, including slow ones, remain in the report.

Build logs, storage reports, a private fixture manifest, environment/build provenance, context, journal and successful summary are retained. Source files remain under the run directory. Generated recovery checkpoints remain in the dedicated performance sandbox's `UITests/<UUID>` roots listed by attempt records. Failed runs also retain every artifact. No automatic fixture deletion or retry occurs. Inspect a failed run and any surviving identified app process before another invocation; never remove normal recovery or infer ownership from a bundle name alone. Paths/bookmarks/fixture text are excluded from the numeric journal and public summary; private manifests must not be published as store evidence.

Normal CI compiles the executable and runs its host-support and repository tests through `swift test` and the existing repository suite. Actual measurements are opt-in and serialize with other native work. Retain dated baseline/candidate evidence with full source and binary provenance before describing a result. Physical display timing, responsiveness during opening, 100 MiB and pathological paragraphs, minimum hardware/OS, real IMEs and energy remain separate release gates.
