# Application performance measurement

Issue [#35](https://github.com/Orbitane-Limited/NoteHush/issues/35) provides repeatable native-app measurements for [#12](https://github.com/Orbitane-Limited/NoteHush/issues/12). The [initial complete baseline](validation/2026-09-07-app-launch-baseline.md) passed all three workloads, exact recovered-buffer verification and 20-sample extraction for both intervals. Separate app-only attached profiling also passed. The [viewport-before-focus comparison](validation/2026-09-07-editor-focus.md#complete-unprofiled-comparison) reduces 5 MiB readiness p95 from 2.24 seconds to 853 ms on this M4 Pro. Minimum-hardware and other product budgets remain open. Storage-only benchmark results do not certify app latency.

## Isolated optimized app

`ReleasePerformance` builds the same AppKit implementation with Swift `-O` and whole-module optimization, using bundle ID `pk.codehub.NoteHush.PerformanceTesting` and bundle/executable names `NoteHushPerformance.app` / `NoteHushPerformance` to avoid Instruments ambiguity with development/UI builds. It requires `NOTEHUSH_TEST_WORKSPACE` to be a UUID before `NSApplication` is created. The directory is derived inside this separate app container; arbitrary paths and reset flags are not accepted. Its run, test, profile, archive and analyze actions all use this configuration. The normal Release app excludes the readiness signpost and workspace environment handling; archive validation checks both metadata and the executable for accidental test controls.

The `NoteHushPerformance` scheme disables its debugger and diagnostic instrumentation for measurement. The functional `NoteHush` CI scheme retains its existing checks, tests and 30/60-second per-case limits. Performance cases have a separate allowance because each performs 20 full launches; this is not a change to a failing functional test's timeout.

`build_performance.sh` compiles the optimized app and test driver without launching either. Normal CI runs this build after its functional tests and shipping archive checks. `verify_performance_build.py` checks resolved build settings and every scheme action. `verify_test_app.py --configuration ReleasePerformance` checks the separate app identity, required workspace marker and exact four product entitlements. Both checks must pass before any performance launch. Test builds are never release archives or App Store candidates.

## Measurements and boundaries

The three cases use an empty tab, 20 open tabs totaling 5 MiB, and 100 open plus 20 closed tabs totaling 30 MiB. Nonempty tabs each contain 256 KiB, alternating unique ASCII and Arabic/combining-mark/emoji CRLF fixtures. The selected tab is deliberately the last tab. The host-only `PerformanceFixtureHarness` first checks missing/invalid workspace rejection, makes untimed launches to register the sandbox container, then seeds each fixture after the app terminates. The sandboxed XCTest runner reads only generated fixture identities and digests from a manifest; it does not write another app's container. Every measured iteration launches a new process against warm filesystem caches. This is not post-reboot cold launch.

Each case requests 20 XCTest measurement iterations. XCTest performs an additional first warm-up iteration and excludes that iteration from its reported measurements; the driver does not remove further samples. Extraction must verify the actual exported sample count and units before calculating an arithmetic middle-pair median and nearest-rank p95. Retain the raw xcresult/CSV/JSON data and identify that framework warm-up. Do not silently accept missing signpost intervals or too few measurements. A performance-only window identifier is published after the readiness endpoint. Collection stops explicitly after that identifier and the restored editor are available and before post-interval assertions or Quit, so the launch metric can detach its event-loop observer while the process is alive.

Report two separate intervals:

- `XCTApplicationLaunchMetric(waitUntilResponsive: false)` reports Apple's first-frame launch metric. NoteHush does not start MetricKit extended launch tasks. An asynchronous recovery operation can outlast the initial window, so this metric does not establish editor readiness. The previously attempted `true` variant omitted samples on this toolchain even when collected alone; those failed results remain in the investigation record and are not combined with this different interval.
- `ProcessToEditorReady` starts in the app entry point after workspace-identity validation and ends after recovery, selected-editor installation, focus, layout and `displayIfNeeded`. This excludes pre-entry loader/LaunchServices work, and its endpoint is an AppKit readiness boundary rather than display scan-out. It must not be relabeled as event-to-visible typing latency or added to an overlapping launch interval.

Static signpost names contain no document content, paths, bookmarks or clipboard data. After the measured intervals, the driver checks selected-tab identity/text, types a generated character into the restored keyboard destination, undoes it and verifies the original digest. It then uses Cmd+Q and verifies both XCTest state and the identified process have terminated. Every iteration must start without a running app; all open/closed buffers are verified after the final normal termination. Generated fixture storage is removed only after the owned test app stops. The suite refuses to take over a previously running performance app.

## Running and retaining evidence

Wait until CI and other GUI automation are finished. Use a logged-in desktop with exclusive keyboard/mouse access, fixed display conditions, AC power and recorded power/thermal state. Do not run the functional UI suite or another local performance run concurrently. Do not stop or inspect unrelated projects to obtain a result.

```sh
bash scripts/test_performance.sh
```

The script validates configuration, builds the optimized app/tests, applies and checks the exact sandbox signature, runs the opt-in suite and exports metrics with `xcresulttool`. The host helper verifies all open/closed buffer digests and selection after normal termination. Only after the entire script succeeds, including extraction, does its exit handler remove the generated performance-workspace directories. Any earlier failure or interrupted exit preserves the manifest/recovery data and original failure status. Cleanup failure also fails the script. Existing manifests or an already-running performance app stop setup; they are never reset by a later run. Logs, provenance and a unique result bundle are retained under `build/logs`. The initial successful result includes 63 functional launch/edit/Undo/Quit cycles and 120 accepted metric samples, with complete conditions and limitations in the baseline report.

The attached-profile driver uses the same success-only fixture cleanup. After a failure, inspect only the retained generated manifest and its UUID-scoped data; never print unexpected text or inspect a normal recovery workspace. Confirm the owned app has stopped before explicitly invoking `PerformanceFixtureHarness cleanup <the isolated app> <that generated manifest>`. Preserve necessary diagnostic copies first. No automatic retry or cleanup of failed evidence is performed. See the [retention regression](validation/2026-09-08-performance-retention.md).

The manually dispatched `Application performance` workflow runs the same command and retains evidence for 14 days. Its job shares the single self-hosted runner with functional CI, so those jobs cannot run concurrently. This does not prevent input from a person, local command or another project; the operator still needs to establish exclusive GUI access. No automatic reruns or latency thresholds are configured.

The scripts record source revision/dirty state, executable hash, macOS/Xcode/Swift versions, hardware model/memory/architecture, cache/power conditions, screen sizes/scales and initial thermal state. Thermal enum values are 0 nominal, 1 fair, 2 serious, 3 critical; the fixture timestamp is Foundation's seconds since 2001-01-01. The record explicitly leaves other GUI input exclusivity unverified. Document sample counts, display changes and competing workloads separately; a dirty checkout is acceptable for harness debugging, not the final reproducible baseline. Compare unprofiled samples separately from Instruments runs. Failure or interruption invalidates that result set; investigate it without trimming slow samples or changing functional assertions.

Power metadata retains only a recognized power source, internal-battery percentage and charging state. Battery identifiers, device names and raw command output are excluded; unfamiliar values remain unknown. These are initial conditions, not continuous monitoring of the full run.

## Instruments protocol

The installed Xcode 26.6 provides App Launch, Time Profiler, CPU Profiler, Allocations and Power Profiler templates. `xctrace record` supports targeting a single launched app or PID, and `xctrace export` exposes a trace table of contents plus XPath-selected tables. Only the independently verified PerformanceTesting app and generated fixtures are in scope. Never use `--all-processes`, attach to an unrelated process, or profile the user's regular NoteHush workspace.

`bash scripts/profile_performance.sh` builds/verifies the app and prepares separate fixtures. The host helper opens the exact app URL through LaunchServices with the generated workspace UUID, validates its returned bundle URL/identifier, and invokes `xcrun xctrace record --template 'Time Profiler' --time-limit 10s --output <unique.trace> --attach <verified PID>` for the 5 MiB workspace. This trace starts after LaunchServices startup and attachment overhead, so it cannot measure the complete launch interval. The unprofiled launch/readiness tests provide those separate timings. After recording, the helper requires the owned app to remain alive, requests normal termination, verifies all recovered fixture buffers and exports the trace table of contents. Only its known process is eligible for forced failure cleanup. It never passes `--all-processes` or `--no-prompt`.

Retain the trace and exported table of contents, inspect the app's samples and document profiler overhead separately. A denied profiling permission or unavailable metric is an unverified gate; do not broaden shipping entitlements or imply a successful trace. The verified PID-attachment protocol passed recording, normal termination and all-buffer verification on source `61cce9f`; all 465 exported sample rows belonged to the intended fixture app. See the setup evidence for that successful protocol and the retained failed launch recordings. These attached samples do not measure complete startup or settled idle CPU.

## Remaining product acceptance

#12 still requires event-to-visible typing, switching, 10/100 MiB and pathological-line behavior, memory/resident footprint, settled 60-second idle CPU/energy, display/font/wrap/spelling/printing responsiveness and 100+ tabs/history operations. The M1/8 GB reference hardware is not available in this session; M4 Pro results cannot silently stand in for it. Minimum-macOS/Intel, VoiceOver, real IMEs and signed TestFlight behavior remain separate open release gates. Do not revise limits or publish speed claims without evidence.

References checked against the installed SDK and official documentation: [XCTApplicationLaunchMetric](https://developer.apple.com/documentation/xctest/xctapplicationlaunchmetric), [first-frame versus responsive endpoints](https://developer.apple.com/documentation/xctest/xctapplicationlaunchmetric/init(waituntilresponsive:)), [OSSignposter](https://developer.apple.com/documentation/os/ossignposter), and [XcodeGen 2.46.0 scheme options](https://github.com/yonaskolb/XcodeGen/blob/2.46.0/Docs/ProjectSpec.md#scheme). Installed `XCTMetric.h` confirms the macOS launch/readiness metric API; `xctrace help record/export` and `xcresulttool export metrics --help` document the CLI used here.

## Interaction protocol

`bash scripts/test_interactions.sh` adds four isolated optimized typing/switching scenarios and strict extraction for native dispatch plus automation round-trip intervals. Follow the [protocol and current validation status](validation/2026-09-07-interaction-protocol.md). The complete four-case baseline passed native correctness, host recovery verification and all 160 observations. Mixed-script dispatch p95 is 182.848 ms for typing and 80.527 ms for switching; physical display latency and minimum-hardware acceptance remain open. The full original launch regression subsequently passed all 63 cycles and 120 observations; the current 5 MiB readiness p95 is 1,012.042 ms, slightly over its one-second target on this Mac. Earlier initialization/capture and unexpected-input failures remain recorded. Final-head CI still blocks merge. The manual workflow offers `launch` and `interaction`; the existing launch protocol and its historical samples remain separate.
